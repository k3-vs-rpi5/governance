# 多仓库评测契约

文档 ID：`repository-contract`
内容修订：`2`
负责人：governance 维护者
评审状态：已批准设计

## 目的与权威

本契约管理 K3 Pico 对比树莓派 5 的评测工作区。目标是可信、可公开审计的性能
对比和 upstream 级优化，而不是生成好看但不受控的分数。

Google `repo` release manifest 选择准确的 governance、foundation、项目和可选
reports 版本。根 `AGENTS.md`、本契约、受影响的项目清单和所选环境锁，是每次开发
会话的必需输入。聊天历史不具有规范权威。

## 仓库边界

工作区根目录不是 Git 仓库。manifest 仓库组合以下独立 Git 仓库：

- governance 拥有规范和 AI/人工协作规则；
- foundation 拥有公共设备、环境、遥测、统计和证据验证；
- 每个评测或优化目标拥有一个项目仓库；
- reports 为每个项目保存一份稳定公开报告和证据索引。

CoreMark 是第一个独立项目，ID 为 `coremark`。不存在 `cpu-foundation` 上层项目。
STREAM、lmbench、OpenSSL、allocator 等套件只有分别通过依赖顺序准入后才能进入。

reports 被分配到 `reports,notdefault`。默认代码迁移和普通 `repo sync` 不传输
报告。release manifest 可以固定 reports revision，在默认不检出内容的同时保持
可追溯性。

## 代码必要性

创建任何源码文件、模块、辅助程序、脚本、fixture、测试或框架前必须询问：

> 这段代码是否必要？如果删除，会破坏哪项已声明契约？

默认答案为否。只有简洁的评审理由指出长期且已批准的契约、证明没有可用的上游或
现有路径、选择最小长期实现、提供确定性验证，并声明 owner 和删除条件时，才允许
新增。计划条目、覆盖率、测试数量、文件对称、假想复用或一次性迁移都不是理由。

## 测试策略

官方和代码自带正确性测试具有权威性。CoreMark 等标准分数使用官方套件和规则。
本地测试不得替代或重新定义官方分数。

本地自动化测试只保护以下长期自有行为：

1. 补丁身份、无模糊应用和反向撤销；
2. 环境与控制变量资格检查的失败关闭；
3. 公开构建/运行入口的可复现性和身份闭环；
4. 已接受证据与报告之间的可追溯性和完整性。

公共契约只在 foundation 测试一次，项目不得复制。静态文案、简单包装、第三方内部
实现、在线硬件事实、一次性迁移，或已经由上游、schema 或更低权威层覆盖的行为
测试必须删除。同类情况参数化到最小有效测试。测试数量和覆盖率绝不是发布目标。

## 文档策略

每份受维护的项目自有 Markdown 都必须完整配对：

```text
name.md
name.zh-CN.md
```

禁止 `.en.md` 后缀、只有标题的混合翻译、孤立配套文件、损坏本地链接，以及命令、
版本、哈希、指标或阈值的重要差异。更新权威文档，不建立内容重叠的新指南。报告
遵循下述独立规则。

## 项目准入与依赖顺序

只有公共 OS/运行时/编译链基础及所有受影响底层依赖通过资格检查后，项目才能开始。
`project.yaml` 声明 owner、依赖层级、上游源码、适用轨道、正确性 oracle、指标、
CPU 集合、遥测、结果模式、风险、偏差和停止条件。

验证永远先于优化。工作从底层库和运行时向依赖它们的库与应用推进。底层依赖不
稳定的项目必须标记为 `blocked`，不得静默晋升。

## 三轨环境契约

每个适用项目必须分开：

1. `rpi-native`：树莓派 5 4 GB、脚本验证本源、固定当前 OS 和较低版本编译链/
   运行时；
2. `k3-compatible`：K3 Pico 使用内容锁定的 rootfs/chroot，以及可获得的最接近
   匹配编译链/运行时软件包；
3. `k3-development`：K3 Pico 使用原生 Bianbu 和固定的较新开发编译链/运行时。

`default-parity` 在三轨使用相同的架构无关源码、工作负载、输入、评测参数、CPU
数量等级、亲和性策略、预热、session、采样和遥测策略。每个架构都记录准确的
编译器、链接器、libc、binutils、运行时、参数和可执行文件身份。重要差异必须成为
明确偏差；解决前不得称结果为严格齐平。

缺失的声明软件包通过固定 APT 源安装。只有锁定版本、来源、digest 和运行时边界
时，才能使用指定上游编译器替代。主机 loader/library 泄漏和静默编译器回退必须
失败关闭。

两台设备统一使用稳定 Type-C 供电和有线网络。CPU 计时排除源码下载、包安装、编译
和存储准备。记录实际 eMMC/UFS/SD 类别和缓存策略；不可避免的 I/O 单独报告。如果
已安装 OS 能可靠执行，就使用显式亲和性实现单核和四核，无需为此制作自定义镜像。

## 结果模式与优化周期

每个项目都分开 `default-parity` 和 `best-achievable`。K3 最佳结果绝不能替代参数
齐平的默认结果。

只有完成以下流程，优化周期才结束：

```text
锁定基线
→ profiler/counter/汇编热点
→ 可证伪假设
→ 单变量候选
→ 上游正确性
→ quick 筛选
→ 正式重复验证
→ 接受或拒绝处置
→ upstream 级补丁
→ 经审核的报告更新
```

评测源码捷径、隐藏负载修改、放宽正确性或未记录环境变化都会使结果失效。优先
通用改进。只有公开披露、归属正确上游，且不修改官方负载源码（除非规则明确允许）
时，才允许合理的平台或编译器改进。

## 项目公开接口

每个项目仓库恰好公开两个 Shell 入口：

```text
scripts/build.sh
scripts/run.sh
```

`build.sh` 获取并验证锁定上游源码、记录完整编译链、通过 APT 安装缺失声明依赖、
无模糊应用有序补丁 manifest、运行上游正确性并封存构建身份。源码不干净、缺少锁、
软件包未验证、补丁 fuzz 或未声明回退都必须失败。

`run.sh` 接收已封存构建和显式绝对本地证据根。它重新验证身份、检查所选环境资格、
先运行官方正确性再运行性能、执行声明的预热和采样、记录遥测并封存只追加候选。
它绝不修改报告或 Git。

禁止额外 Shell helper。只有通过代码必要性门禁后才能增加非 Shell 项目逻辑。复现
步骤归项目 README 文档对所有。

## 测量与证据

每个正式候选记录板卡/CPU 身份、架构与拓扑、在线核心与亲和性、可见内存、配置及
采样频率、平均温度、governor、throttling、swap、服务、OS、内核、loader、libc、
编译器、链接器、参数、可执行文件摘要、运行时 profile 摘要、rootfs/sysroot 身份、
内存带宽背景、存储、有线网络、官方套件/源码/校验和、命令、预热、session、样本、
统计、偏差和评审状态。

未知必填信息必须写为 `not-recorded` 并说明原因；当其影响解释时不得正式晋升。
失败或中断运行在本地保留为 `invalid` 或 `blocked`。设备重启、替换、温度/频率
不稳定、遥测缺失、运行时漂移、校验失败或官方正确性失败都要求重新资格检查。

## 报告策略

独立 reports 仓库为每个项目保存一份稳定逻辑报告：

```text
<project-id>/report.md
<project-id>/report.zh-CN.md
<project-id>/report.yaml
<project-id>/evidence/index.yaml
```

禁止日期、周期、`latest`、`related` 或 revision 报告目录。报告对原位更新，Git
历史就是继承轨迹。`report.yaml` 固定 manifest、governance、foundation、project、
源码、编译器、补丁和证据身份。已接受精简证据不可修改，并按内容寻址。外部大型
日志必须记录稳定位置、SHA-256、字节数和可用状态。

只有经过人工审核的晋升才能更新报告。项目执行不得修改报告。缺失证据不能用名称
相似的运行替代；复现前该结论必须保留为限制或 `blocked-retest`。

## Git 与迁移策略

官方迁移方式是使用已批准 manifest 执行 `repo init`，随后执行 `repo sync`。直接
复制工作区不是官方方式，因为它可能包含被忽略的秘密和不受控状态。根协作文件由
manifest 从 governance 复制。

拆分历史前必须创建并验证被忽略的恢复 bundle。每个目标仓库的源目录只有通过基本
验证后才能获得第一次干净提交。现有单体仓库历史留在恢复 bundle，不注入新组件
历史。

不得隐式配置网络 remote 或 push。准确 remote URL、分支和 refspec 必须在干净
release-manifest 同步后由人工批准。凭据、私有清单、编译链下载、缓存、构建、本地
候选和恢复资料绝不能进入受管 Git 仓库。

## 完成门禁

组件只有通过适用的文档、语法、上游、补丁、包和聚焦契约检查后，才可建立第一次
干净提交。项目只有通过正式三轨证据、默认/最佳分离、环境偏差审核、独立复现、双语
报告审核和证据身份闭环后，才可公开结果。

只有不可变 release manifest 能在干净工作区重建同一代码版本、默认同步不包含
reports、显式同步可取得固定报告、根协作规则存在、受跟踪内容无秘密，且人工 owner
批准远端操作时，完整工作区才可首次 push。
