# Repo 工作区架构

文档 ID：`repo-workspace-architecture`
内容修订：`1`
负责人：仓库维护者
评审状态：已批准的设计候选

## 目的

本文档定义将整个 K3 对比树莓派 5 的评测工作区迁移到 Google `repo`
管理模式的已批准目标架构。它将治理、公共验证基础设施、评测项目和报告拆分为
独立 Git 仓库，同时保持一个可复现的完整工作区以及既定的 AI/人工协作模式。

本设计取代以下现行规则：将 CoreMark 作为 `cpu-foundation` 内部周期、将报告
存放在代码仓库，或把当前单体仓库根目录作为最终 Git 所有权边界。在实施计划
替换冲突章节之前，这些旧文档仅作为迁移输入。

## 范围与非目标

迁移单位是通过固定 manifest 重建的完整 `k3Vrp5` 工作区。CoreMark 是第一个
独立的评测与优化项目。STREAM、lmbench 等后续套件只有分别通过项目准入评审后，
才能成为独立项目。

本设计不会：

- 复制凭据、缓存、构建产物、本地候选结果或未经审核的原始运行；
- 在默认代码迁移中携带报告；
- 为归集互不相关的 CPU 套件而创建一个项目；
- 设置测试数量或覆盖率目标；
- 在正式证据审核前授权公开性能结论。

## 仓库拓扑

工作区根目录由 Google `repo` 管理，其自身不是 Git 仓库。

```text
k3Vrp5/
├── .repo/                      repo 元数据及选定的 manifest
├── AGENTS.md                   由 manifest 从 governance 复制
├── governance/                 规范与协作 Git 仓库
├── foundation/                 公共验证 Git 仓库
├── projects/
│   └── coremark/               独立 CoreMark Git 仓库
└── reports/                    可选且非默认的报告 Git 仓库
```

manifest 仓库是版本集合的权威来源。它定义仓库 URL、路径、分组和版本。开发
manifest 可以跟踪经过审核的分支。每个可复现或公开基线都使用 release manifest，
且其中的项目版本均为不可变 Git commit ID。

`reports` 项目同时归入 `reports` 和 `notdefault` 分组。普通初始化和同步不包含
该项目。只有需要查看报告时，审核者才显式选择 reports 分组。release manifest
可以固定 reports commit，从而在普通迁移不传输报告内容的前提下，仍可交叉检查
代码与报告身份。

## 仓库职责

### Manifest 仓库

manifest 仓库只负责工作区组成：

- 项目名称、远端、路径、分组和版本；
- 开发 manifest 和不可变 release manifest；
- 将 governance 中的 `AGENTS.md` 物化到根目录的 `copyfile` 规则；
- 重建同步工作区所需的版本集合元数据。

它不拥有评测逻辑、环境检查、报告或重复的规范正文。

### Governance 仓库

governance 仓库拥有完整的中英文规范文档对、项目准入规则、AI/人工协作契约、
目录与文档规则以及评审清单。其权威 `AGENTS.md` 通过 `repo` 复制到工作区根目录，
使新同步的工作区无需依赖聊天历史或机器本地记忆即可恢复协作模式。

### Foundation 仓库

foundation 仓库拥有公共设备资格检查、环境配置、三轨对比契约、遥测与证据
schema、公共验证器，以及经过必要性证明的最小自有测试集合。它不拥有评测项目
特定的补丁、分数解析或报告。

### 项目仓库

每个获准的评测或优化目标拥有一个独立 Git 仓库。第一个是
`projects/coremark`。项目拥有源码与工具链锁、两个公开入口、项目特定适配、已接受
补丁、复现说明，以及保护长期项目特定契约所必需的最少测试。

仓库独立是指独立所有权和 Git 历史。正式结果只认可由 release manifest 选定的
完整工作区；任意单独克隆的项目仓库不构成受控的正式环境。

### Reports 仓库

reports 仓库拥有每个获准项目经过审核的公开结论和公开证据索引。它不包含评测
运行器，也不复制 foundation 验证器。该仓库与代码分别维护、分别迁移。

## AI/人工协作契约

协作模式属于仓库状态，而不是对话状态。根目录 `AGENTS.md` 定义公共权限边界和
工作流。项目可以提供限制更严格的项目级 `AGENTS.md`，但不得放宽治理、验证、
安全或发布要求。

开始工作时，AI 或人工贡献者必须读取选定的 manifest、治理契约、项目清单和当前
证据状态。AI 可以检查、实施已经批准的修改、执行范围内验证并准备评审材料。项目
准入、架构修改、接受环境偏差、向 reports 仓库晋升、破坏性清理、选择远端和首次
推送仍必须由人工批准。

重新同步后仍需使用的决策必须记录在受跟踪的契约、manifest 和评审记录中。测量
细节记录在本地封存证据中。聊天历史绝不能成为需求、批准、例外、结果或下一步行动
的唯一记录。无论 AI 还是人工评审，都不能直接豁免官方正确性或证据门禁；如需改变，
必须通过相同的受审核设计流程修改治理契约。

## 单一项目、单一报告

每个项目只有一份稳定的逻辑报告。英文和中文文件是同一报告的两种完整语言表达。

```text
reports/
└── coremark/
    ├── report.md
    ├── report.zh-CN.md
    ├── report.yaml
    └── evidence/
        ├── index.yaml
        └── <content-digest>/
```

报告文件原位更新。禁止使用日期、`latest`、`final-v2`、`related` 目录或并行的
当前报告。Git 历史就是继承关系和审计轨迹。`report.yaml` 记录当前结论使用的
manifest、项目、foundation、源码、工具链、补丁和证据的精确身份。

已经发布的精简证据不可修改。新接受的证据使用新的内容寻址目录。大型完整日志
可以存放在外部归档，但证据索引必须记录稳定位置、SHA-256、字节大小和可用状态。
缺失、不稳定或未通过资格检查的运行保留在本地候选区，不得进入 reports 仓库。

## 三轨环境契约

每个项目必须运行以下三个轨道，或明确标记技术上不适用：

| 轨道 | 目的 | 必需环境 |
|---|---|---|
| `rpi-native` | 脚本验证本源与可比默认结果 | 树莓派 5 4 GB、固定的当前 OS、固定的较低版本编译链与运行时 |
| `k3-compatible` | 与树莓派 5 进行严格控制变量对比 | K3 Pico 使用锁定的 rootfs/chroot，并拉齐软件版本、源码、参数和流程 |
| `k3-development` | K3 主要开发与最佳可达结果 | 原生 Bianbu 和固定的较新编译链与运行时，记录所有重要版本 |

环境齐平绝不声称 Arm64 与 RISC-V 使用相同二进制。齐平按以下顺序建立：

1. 相同的上游源码版本、补丁状态、工作负载和输入数据；
2. 在两个架构都能提供时，使用相同的编译器发行版本、链接器、构建选项和语言
   运行时；
3. 在两个架构支持的范围内，使用相同的发行版套件、软件包版本和库配置；
4. 使用相同的 CPU 数量等级、亲和性策略、迭代次数、预热、遥测、网络策略和
   后台服务策略；
5. 明确记录内核、libc、binutils、CPU 频率、温度、内存、swap、存储、节流以及
   所有无法避免的差异。

尚未解决的重要差异必须写入偏差记录，相应结果不得描述为“严格齐平”。

K3 compatible 环境使用隔离且内容锁定的 rootfs/chroot，不替换 Bianbu 主机环境。
缺少的编译链软件包通过固定的 APT 源安装。如果两个架构无法取得同一软件包版本，
只有在锁定其源码、版本、下载来源和 SHA-256，并披露剩余运行时差异时，才能使用
指定的上游工具链。

## 必需结果模式

每个项目保留两个相互独立的结果模式：

- `default-parity` 在三轨使用相同的官方源码、工作负载、参数、CPU 策略和允许的
  优化等级；
- `best-achievable` 记录通过公开且技术上合理的编译器、运行时、ISA 或可上游化
  源码工作取得的最佳有效 K3 结果。

最佳可达结果绝不替代默认齐平结果。平台特定的跑分捷径、隐藏的负载修改、放宽的
正确性规则或未记录的环境变化都会使结果失效。

## 子项目开发周期

每个项目遵循以下顺序：

```text
必要性审查
→ 依赖层级与项目准入
→ 上游正确性测试
→ 在树莓派 5 验证编译/运行脚本
→ 树莓派 5 默认基线
→ K3 compatible 默认基线
→ K3 原生默认基线
→ profiler、热点与汇编分析
→ 单变量候选优化
→ 正确性与回归验证
→ upstream 级补丁整理
→ 三轨正式复现
→ 经审核后更新 reports 仓库
```

每项优化形成一个完整闭环：假设、单变量实验、证据、结论以及接受或拒绝的补丁
处置。工作自底向上开展。当受影响的底层正确性或环境契约尚未通过资格检查时，
不得优化上层项目。

树莓派 5 是公开脚本行为的验证本源。Bianbu 是 K3 主要开发环境。正式结论必须
覆盖全部适用轨道，不能只提供产生最佳分数的环境。

## 项目仓库契约

项目公开以下稳定职责，且不复制 foundation 行为：

```text
projects/<project-id>/
├── project.yaml
├── README.md
├── README.zh-CN.md
├── sources.lock.yaml
├── environments.lock.yaml
├── scripts/
│   ├── build.sh
│   └── run.sh
├── patches/
│   ├── README.md
│   ├── README.zh-CN.md
│   ├── manifest.yaml
│   └── *.patch
├── src/                         仅保留有必要性的项目特定逻辑
└── tests/                       仅保留有必要性的项目特定契约测试
```

`build.sh` 是唯一公开构建入口。它获取锁定的上游源码、验证完整性、取得声明的
编译链、无模糊地应用有序补丁系列、运行上游正确性检查，并封存构建身份。

`run.sh` 是唯一公开执行入口。它使用已封存构建、调用 foundation 资格检查、在
性能采样前运行官方正确性验证、执行声明的预热和重复、采集必需遥测并封存候选证据。
它绝不修改报告。

禁止额外的 Shell 辅助程序。只有当必要性门禁证明某项行为无法在现有组件中保持
清晰与可靠时，才允许增加非 Shell 辅助程序。

## 代码与测试必要性门禁

在创建任何源码文件、模块、脚本、辅助程序、fixture、测试或框架前，AI 或人工
作者都必须回答：

> 这段代码是否必要？如果删除，会破坏哪一项已声明契约？

默认答案为否。新增代码必须用一句简洁理由说明其保护的长期契约、为何上游或现有
实现不足、确定性验证方法、负责人和删除条件。

测试数量和覆盖率不是目标。首先使用上游或官方测试。只有为了保护以下长期自有
边界时，才允许增加本地自动化测试：

1. 补丁无模糊应用和反向撤销；
2. 对无效控制变量或环境进行失败关闭；
3. 两个公开入口的可复现性和身份闭环；
4. 已接受证据与报告结论之间的可追溯性。

公共边界只在 foundation 测试一次，项目不得重复。禁止测试简单包装层、静态文案、
第三方实现细节、一次性迁移代码，或已经由官方套件或更低权威层覆盖的行为。同类
情况应参数化到最小有效测试中，不得扩张为额外文件。

## 证据流与失败处理

测量输出首先成为本地候选证据。候选结果只有通过 schema 验证、环境资格检查、
上游正确性、校验和闭环及人工审核后才能晋升。晋升操作把精简的已接受证据复制到
reports 仓库，并在同一次审核变更中更新唯一报告对和 `report.yaml`。

失败或中断的运行在本地保留明确的 `invalid` 或 `blocked` 状态及原因。它不能被
静默丢弃、转化为部分成功或被报告工具选用。设备替换、重启、温度不稳定、频率不符、
工具链漂移、主机库泄漏、遥测缺失或官方测试失败，都会使受影响的正式 session
失效，并要求重新资格检查后再试。

## 迁移与 Git 历史

官方迁移机制是针对选定 manifest 执行全新的 `repo init`，然后执行 `repo sync`。
直接复制旧工作区不是官方迁移方式，因为它可能携带被忽略的秘密、陈旧对象和不受控
结果。

迁移按以下顺序进行：

1. 冻结当前工作树，不推送，也不删除可恢复证据；
2. 将每个保留路径分类为 manifest、governance、foundation、project、report、
   仅本地或废弃；
3. 解体 `cpu-foundation`，把公共行为迁入 foundation，把 CoreMark 行为迁入
   `projects/coremark`；
4. 把唯一经过审核的报告和已接受证据迁入 reports；
5. 删除绝对路径和对当前单体仓库根目录的假设；
6. 准备候选独立仓库和本地候选 manifest；
7. 在默认排除 reports 的条件下复现一个全新工作区；
8. 验证 CoreMark 源码获取、补丁重放、构建、快速运行、证据校验和 AI/人工规则
   发现；
9. 只有完成以上步骤后，才在各仓库创建第一次干净提交。

现有单体仓库历史只保存在被忽略的恢复 bundle 中，不注入新仓库历史。任何仓库
在基本验证通过且准确远端 URL、分支和 refspec 获得批准前都不得推送。最终
manifest 禁止包含占位远端。

权威公开托管位置是 `https://github.com/k3-vs-rpi5`。同级仓库名称为
`governance`、`foundation`、`coremark`、`reports` 和 `manifests`，权威分支为
`main`。manifest remote 继续使用同级相对路径，从该组织即可解析全部仓库。本地
checkout 使用 GitHub 作为 `origin`。已有私有 Gitea remote 可以作为 `gitea` 保留，
用于恢复或明确执行的镜像操作，但它不定义公开 revision，也绝不被 release
manifest 选择。

凭据和私有设备清单位于所有受管 Git 仓库之外。缓存、已下载工具链、构建工作区、
本地候选证据和恢复 bundle 同样排除。根目录协作文件由 governance 可复现生成，
而不是依赖未跟踪的本地惯例。

## 验收标准

只有以下条件全部满足，才视为完成架构实施：

1. 默认 `repo` 同步不包含 reports；
2. 显式选择 reports 分组后取得固定的 reports commit；
3. 全新工作区获得权威根目录 `AGENTS.md`；
4. governance、foundation、CoreMark、reports 和 manifest 具有独立 Git 历史和
   明确所有权；
5. CoreMark 只公开一个构建入口和一个运行入口；
6. 锁定的补丁系列能够对已验证上游源码无模糊应用和反向撤销；
7. 所有适用轨道都记录编译器、链接器、libc、运行时、参数和环境偏差；
8. `default-parity` 与 `best-achievable` 始终分开；
9. 每个保留的本地测试都能指出一项允许的长期契约；
10. 默认代码迁移不会传输任何秘密、缓存、临时日志、候选结果或报告；
11. 唯一 CoreMark 报告对把每项当前结论追溯到已接受证据和准确仓库版本；
12. 不可变 release manifest 可以在干净工作区重建同一代码版本集合；
13. 公开 GitHub manifest 可以重建默认不含 reports 的工作区，而显式
    `default,reports` 同步可以取得 reports。

## 对当前目录的影响

实施期间必须重写当前的 `docs/repository-contract*`、`docs/repository-layout*`、
`docs/project-requirements*` 和 `docs/repository-consolidation-plan*` 文档对。尤其要
删除以下旧规则：

- 把 CoreMark 视为 `cpu-foundation` 周期，而不是独立项目；
- 把报告和原始结果放在代码单体仓库；
- 使用单体仓库 Git 历史和最终两个 commit 的形态；
- 在项目中重复公共验证和报告检查。

继续有效的规则包括：优先使用上游测试、精确记录编译链身份、严格三轨控制变量
对比、分开默认结果与最佳结果、整理 upstream 级补丁、完整中英文文档，以及代码/
测试必要性门禁。
