# 项目生命周期

## 入项门禁

只有共享 OS/运行时/编译链基础通过，且更底层依赖稳定后，项目才可开始。入项卡
必须声明 owner、上游源码与版本、依赖层级、支持轨道、正确性 oracle、主指标和
方向、结果模式、CPU 集合、遥测、raw schema、风险和停止条件。

优先使用代码自带测试；CoreMark 等标准 benchmark 使用官方套件。只有删除本地测试
会导致一项长期自有契约失去保护时才允许保留；在最低权威层使用最小确定性用例，
不得重复上游覆盖。

## 预注册矩阵

首次性能运行前必须冻结：

1. `rpi-native`、`k3-compatible` 和 `k3-development` 的运行时身份；
2. `default-parity` 与 `best-achievable` 规则；
3. 源码 commit、补丁 manifest、编译器/linker/libc、flags 和 CPU 集合；
4. 预热、session、样本、最短时长、种子和验收统计规则；
5. 频率、温度、内存、带宽、throttling、swap、perf 和 I/O 遥测；
6. 官方正确性命令、外部证据根格式、校验和与 reports 仓库身份。

## 验证到落地周期

每个候选都遵循同一完整周期：

1. 复现锁定基线并验证其身份；
2. 使用 profiler、counter 和汇编/编译器证据定位热点；
3. 提出一个可证伪机制和预期受影响指标；
4. 实施最小通用改动并运行官方正确性测试；
5. 用 quick 运行筛选，只有通过预定义门槛才晋级；
6. 在所需轨道与 control 上运行正式重复测量；
7. 落地 upstream-ready 补丁/lock，或记录拒绝理由与 raw-run ID；
8. 只使用公开构建/运行脚本和文档进行独立复现。

分数仅仅提高并不表示周期结束。只有机制、正确性、统计结果、环境身份、补丁、
复现和报告全部一致时，周期才完成。

## 审阅与固化

项目 owner 必须审阅源码完整性、补丁顺序与零 fuzz 重放、编译器版本、运行时摘要、
CRC 或上游正确性结果、样本质量、遥测、基线/优化结果隔离、限制以及两种语言报告。
只有技术上不适用的轨道才允许把必填项写为 `blocked`；不得因设备暂时不可用而跳过。

项目基本验证通过后，独立项目仓库才可获得第一次干净提交。报告状态只有在正式证据
和人工审核通过后，才能在独立 reports 仓库中修改。首次推送仍必须等待干净的
release-manifest 同步和明确的远端批准。

## 上游交付

接受的优化补丁必须按目标上游贡献规范重排和说明。每个补丁都必须最小、通用、
可二分、可独立测试，不得伪造 benchmark 结果，并附精确复现证据。若正确 owner
是编译器项目，编译器改进必须落到编译器项目；工作负载源码诊断不得伪装成官方
分数补丁。
