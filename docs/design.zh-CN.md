# 验证体系设计

## 目标

实验室在控制变量且可审计的条件下对比树莓派 5 与进迭时空 K3 Pico，并把经过
验证的 K3 改进整理为符合上游规范的补丁。软件只报告性能；外部测得的功耗证据
可以附加，但不得改变软件结果契约。

## 自底向上的依赖顺序

优化必须沿软件依赖图推进。选择项目之前先验收基础环境；底层运行时和库先于其
依赖的应用。只有在官方或代码自带正确性测试、测量方法、环境控制、失败策略和
原始证据格式都定义后，组件才允许进入路线图。

固定顺序如下：

1. 验收已安装 OS 身份、运行时 profile、编译链、CPU 亲和性和遥测；
2. 验收 CPU、内存、排除存储影响和网络控制；
3. 使用代码自带测试验证叶子库或官方套件；
4. 定位热点并提出可证伪的优化机制；
5. 筛选候选、晋级统计可信结果并落地补丁；
6. 只有底层稳定后才验证依赖它的上层库和应用。

## 三轨控制模型

每个项目分开 `rpi-native`、`k3-compatible` 和 `k3-development`。
K3 齐平轨运行锁定的低版本 Debian rootfs 与编译链，并在两个架构公开包允许的
范围内尽可能匹配树莓派。K3 开发轨使用当前 Bianbu 运行时和较新编译器。CPU
集合明确绑定为单核或四核；因为当前 K3 使用 UFS 2.2、树莓派使用 SD 卡，存储
密集阶段必须排除在计时区间之外。

## 单项目周期

一个周期包含预注册、默认齐平测量、热点证据、候选验证、正式确认、补丁落地、
独立复现和中英文报告。`default-parity` 保持源码、移植层、flags 类别、参数、
种子、时长、CPU 集合与遥测一致。`best-achievable` 是单独标记的 K3 优化结果。
CoreMark 的 K3 研究目标仍是 `7.7+ CoreMark/MHz`；仅达到正常性能并不代表完成。

## 信任边界

默认使用官方或上游随代码提供的套件。只有上游测试不充分，且本地测试具备对抗
fixture、负向路径、确定性结果、同行复核和已记录 oracle 时，才允许采用本地测试。
存在官方套件时，脚本不得自创替代 benchmark。凭据、下载的编译链、原始运行和
恢复产物不得进入 Git。

## 发布模型

每项结论都必须能追溯到不可变 raw run、精确源码与补丁身份、编译器/linker/libc
版本、运行时 profile 摘要、环境样本和公开构建/运行入口。governance、foundation
和每个项目具有独立 Git 历史，由 Google `repo` release manifest 选择。报告位于
单独的非默认仓库。每个项目只有一份原位更新的稳定逻辑报告；带日期的本地证据只
允许追加。干净的默认同步不包含 reports，并且必须在首次公开推送前重建已接受的
代码版本集合。
